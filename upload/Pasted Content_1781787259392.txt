PART 4 – DYNAMIC PRODUCTAWARE REQUEST FORM
4.0 Purpose & Design Philosophy
The Dynamic ProductAware Request Form is the entry point for every trade. It uses AIdriven dynamic schema generation to adapt the form in real time based on the selected product, origin, destination, port, and any special requirements (e.g., cold treatment, fumigation, specific certificates). The buyer never needs to research regulations manually – the system prepopulates the required fields, documents, and lab tests. Moreover, the form dynamically generates the exact fields needed for the packing list – such as pallet size, number of pallets, cartons per pallet, layer arrangement, and packaging details – tailored to the specific commodity and its handling requirements.
Key principles (nonmarketplace):
• One source of truth – all structured container and commodity data stored in trade_requests.parsed_specs JSONB; reused throughout the workflow.
• AI dynamically builds the form – required documents, commodityspecific fields, lab tests, special conditions, and packing fields are added automatically based on the product and route.
• AI never suggests “you might also want to export to X” or “other buyers used Y”.
• Autodetection of special procedures – e.g., if the destination country or port requires cold treatment, fumigation, or precooling, the system adds the necessary fields and document requirements.
• Dynamic packing specification – for each commodity, the system asks for pallet dimensions (EUR, ISO, custom), number of pallets, cartons per pallet, layers, stacking height, and packaging type – all derived from productspecific defaults and RIA data.
• Multicommodity, multicontainer – supports unlimited containers and unlimited commodities per container.
• Multishipment ready – optional schedule builder for future deliveries.
• Draft autosave – every 30 seconds, resumes via Smart Inbox.
• Incoterm selection – buyer selects incoterm at the start, which determines logistics responsibilities later.
The form is buyerfacing (Trader Portal, Buyer mode) but the data is stored and reused throughout – for seller’s packing, customs declaration, invoice generation, and financing. No data reentry across phases.
AI Integration in Part 4:
• A1 (Groq → Ollama): Autocomplete, dropdown population, default value recommendations, live market charts, AI Container Advisor.
• A2 (HF local → Ollama): Regulatory Intelligence Agent (RIA), Product Form Agent, dynamic JSON schema generation, lab test MRL validation.

4.2 Incoterm Selection (Buyer Responsibility)
Location: Immediately after seller selection, before container entry.

• Which logistics services are the seller’s responsibility vs. the buyer’s responsibility.
• Which costs must be included in the seller’s quote (e.g., for CFR, seller must include sea freight; for FOB, seller only up to loading on vessel).
• Default SGTX fee payer (always seller’s side, but incoterm affects trade value calculation).

4.3 Product Form Agent (A2) – Dynamic JSON Schema Generation
When the buyer selects a product (by typing a product name or HS code), the frontend calls the Product Form Agent (via ai-agent-orchestrator). The agent:
1. Queries the RIA vector database for all relevant regulations for that product, origin, destination, and port – including:
o Required documents (phyto, health, COO, EUR1, cold chain log, treatment certificates).
o Special procedures (cold treatment, fumigation, irradiation, precooling).
o Productspecific dynamic fields (variety, grade, brix, size range, etc.).
o Packing defaults – pallet type, cartons per pallet, net weight per carton, stacking height, packaging types.
o Lab tests required (analytes with MRLs).
2. Calls Groq (fallback Ollama) with a prompt that includes the retrieved context.
3. Returns a JSON schema that defines:
o required_documents (with auto_generate flag and trigger if applicable, e.g., trigger: "COLD_TREATMENT_CERT").
o dynamic_fields (type, options, min, max, mandatory, default) – includes productspecific attributes and packing fields.
o lab_tests_required (analyte, MRL, unit).
o special_conditions (e.g., “Cold treatment required”, “Fumigation required”, “ISPM 15 required”).
o treatment_details (e.g., { "type": "cold_treatment", "temperature_c": -0.5, "duration_days": 14, "certificate_required": true }).
o packing_defaults (e.g., { "pallet_type": "EUR", "cartons_per_pallet": 40, "net_weight_per_carton_kg": 10, "stacking_layers": 5, "max_pallets_per_container": 22 }).
Prompt template (simplified – never suggests counterparties):
text
You are the SGTX Product Form Agent. Generate a JSON schema for a trade request form.
Product: Fresh oranges (HS 0805.10)
Origin: EG (Egypt)
Destination: JP (Japan)
Port of loading: Damietta
Port of discharge: Tokyo
Include:
- required_documents: list of document types. If cold treatment is required, add COLD_TREATMENT_CERTIFICATE.
- dynamic_fields: productspecific attributes (variety, grade, brix, size range) AND packing fields (pallet type, cartons per pallet, net weight per carton, stacking layers, total pallets, packaging type)
- lab_tests_required: analytes with MRLs (from Japan import requirements)
- special_conditions: any routespecific rules (e.g., "Cold treatment required: -0.5°C for 14 days", "Precooling certificate required")
- treatment_details: structured object if applicable
- packing_defaults: default values for pallet type, cartons per pallet, net weight per carton, stacking layers, max pallets per container
Do NOT include any marketplace suggestions (e.g., "you might also export to..."). Return only valid JSON.

4.4 Structured Container & Commodity Entry (Dynamic Form)
The form is fully dynamic – fields appear and disappear based on the product and destination requirements. The buyer can specify:
• Number of containers (default 1, max 50) – each container gets a tab.
• Percontainer fields:
o Country of Origin (global dropdown, filtered by sanctioned list)
o Destination Country (global dropdown)
o Port of Discharge (dependent dropdown, filtered by destination country)
o Palletized? (Yes/No toggle; if Yes, Pallet Size dropdown: EUR, ISO, Custom)
o Destination Override (optional free text, e.g., “Tokyo Free Zone”)
• Commodities within container (unlimited):
o Commodity Type (dropdown – dynamically filtered based on user’s typical products, but never from “other users”)
o Product (combined input: HS code or product name). Entering HS code autofills product name from HS database.
o Dynamic specification fields (generated by AI – includes variety, grade, brix, size range, packaging type, and packing fields)
o Packing fields (pallet type, cartons per pallet, net weight per carton, stacking layers, total pallets)
o Treatment details section (if applicable) – shows temperature, duration, accepted facilities, and requires certificate upload.
o Packaging (dropdown + free text for “Other”)
o Number of pallets for this commodity (already captured in total pallets)
o Net weight per unit (with unit selector: kg / lb)
o Gross weight per unit (autocalculated from net + tare factor, but user can override)
o Notes per commodity (optional)
UI enhancements (nonmarketplace):
• Clone Container – copies all data (origin, destination, port, palletized status, pallet size, and all commodities) to a new container. Useful for repeat shipments.
• Bulk Edit – for 10+ containers, allows applying same commodity to all containers, or copying container settings to a range. No AI suggestions for “typical configurations”.
• Draganddrop reordering of container tabs.
• Progress indicator – shows how many containers are fully configured.
• Inline validation – port must exist, pallet count positive, net weight >0. For cold treatment, the start date must be before the completion date, and the treatment duration must match the requirement.

4.6 MultiShipment Request (Buyer Option)
Below the container form, an optional toggle “Request multishipment contract” (default: off) reveals a schedule builder. The buyer defines a list of future shipments, each with:
• Shipment number (autoincremented)
• Delivery date (future date only – date picker with autocomplete from user’s calendar, no AI suggestions for “optimal dates”)
• Port of discharge (dropdown, can differ from the main form)
• Number of containers for this shipment (integer ≥1)
• Commodities / packaging (by default inherits from the main container definition; but buyer can click “Edit commodities” to override per shipment – opens a miniform with same dynamic fields as percontainer commodity entry, including any special procedures and packing fields)
The schedule is stored as JSONB in trade_requests.multi_shipment_schedule. The total contract value is not calculated until the seller provides logistics costs per shipment (Phase 2). The seller can later modify the schedule.

4.7 AI Container Advisor (A1 – Advisory Only)
After the buyer enters commodity volumes (e.g., “22 pallets of oranges”), the system may display an advisory banner generated by Groq (fallback Ollama). The banner suggests an optimal container count and type based on:
• Total number of pallets
• Pallet dimensions
• Commodity type (perishable, frozen)
• Historical loading density (anonymised, aggregated from optin data, with differential privacy)
Important: This is purely advisory. The buyer can accept (autoadjusts container count) or ignore. The system never says “other buyers used 3 containers” – it only uses anonymised aggregates.

4.8 Marketplace Relationship Detection (AutoAttribution) – For API Partners Only
If the trade originated from a marketplace partner (e.g., an external platform that integrated the SGTX API), the system may display a transparency banner. This is not a recommendation – it’s a legal requirement for revenue share attribution.
When triggered: The system queries partner_lead_attributions for the most recent marketplaceintroduced trade between the same buyer and seller (within 12 months). If found, a banner is displayed:
text
┌─────────────────────────────────────────────────────────────────┐
│ ℹ️ Marketplace Attribution                                      │
│ This trade will be attributed to [TradeBridge] because you      │
│ first connected through them on [2025-12-01]. The standard      │
│ revenue share of [0.5%] will be applied. If you believe this    │
│ is incorrect, you have 72 hours to dispute.                     │

If the buyer clicks “Dispute Attribution”, a form opens to provide a reason. The dispute is analysed by AI (A2) and, if necessary, escalated to the Platform Governance Authority. Attribution becomes final after 72 hours if no dispute is filed.
Crucially, this banner never suggests “you should trade with this counterparty again” – it only informs about an existing attribution.
AI Authority: A2 for dispute analysis (HF local → Ollama).
 
4.9 Governor PreScreen & Submission
When the buyer clicks “Submit Trade Request”, the Governor evaluates:
1. OPA Policy Check:
o Permission trade.request.create
o Active trader mode context = BUY (if dualmode)
2. WasmEdge Constitutional Gate:
o Jurisdiction of buyer, seller, and each port of discharge (including multishipment ports) must not be in autoblock list.
o Each port must exist in ports table and be active.
o Dualuse goods screening (if HS code entered) – if flagged, verdict becomes CONDITIONAL.
o Incoterm validation – the selected incoterm must be valid and compatible with the declared ports.
3. AI Consult (A2 – only if triggered):
o For dualuse HS codes, AI adds conditions for licence.
o For incompatible commodity mixing (e.g., apples and kiwis without separators), AI issues a warning; buyer must explicitly acknowledge.
o For missing treatment data (e.g., cold treatment required but no certificate upload planned), AI adds a condition.
o For packing data consistency: checks that total net weight calculated from pallet fields is consistent with declared total weight (within tolerance).
4. GNN Risk Check:
o If the GNN risk engine is enabled (Addon 1), it checks sanctions proximity between buyer and seller. If proximity ≤2 hops, verdict becomes CONDITIONAL with explanation.
5. Decision Merger & Tenant Message Generation:
o If ALLOW: trade request created with status = 'PENDING_SELLER_RESPONSE'. USTN not yet generated (will be generated at contract lock). The seller receives a Smart Inbox item (priority 75).
o If CONDITIONAL or DENY: Governor generates a plainlanguage tenant_message (A1, Groq → Ollama) listing unmet conditions (e.g., “Cold treatment certificate required – please upload before submission”, “Port of discharge for container 2 is not valid for Japan”, “Calculated net weight (8,800 kg) does not match declared total (10,000 kg)”). The buyer sees the PlainLanguage Governor Decision Panel and cannot proceed until conditions are resolved.

AI Authority: A2 for dualuse and compatibility checks (HF local); A1 for tenant message generation (Groq → Ollama); A4 for OPA and WasmEdge.
 
4.10 Draft AutoSave & Recovery
Every 30 seconds (debounced), the current form state (including all dynamic fields, packing details, and treatment details) is saved as a draft in the trade_requests table with status = 'DRAFT'. The draft includes:
• parsed_specs (partial or complete, including packing defaults and treatment details)
• multi_shipment_schedule (if any)
• updated_at timestamp
Resume workflow:
• When the buyer returns to the portal, the Smart Inbox shows a lowpriority item (score 30): “Continue draft trade request from [date]”. Clicking it opens the form with the saved data.

AI Authority: None (rulebased autosave).
 
4.11 Integration with Other Phases
The data entered in this form flows directly into:
• Phase 2 (Seller Quote): seller sees the buyer’s parsed_specs to lock EXW price and design packing. The packing fields (pallet type, cartons per pallet, stacking layers) are used to generate the packing list and SSCC barcodes. The special procedure requirements (e.g., cold treatment) are displayed to the seller so they can arrange the necessary services.
• Phase 3 (Contract): the structured data populates the customs declaration and commercial invoice. Treatment certificates become mandatory documents.
• Phase 4 (Financing): financiers see the commodity, volume, incoterm, and any special procedure requirements (as risk factors).
• Phase 5 (Execution): the system may add milestones for treatment verification (e.g., “Cold treatment certificate uploaded”).
• Phase 7 (Distressed Cargo): if cold treatment fails, the system can autodeclare distressed based on sensor data.
No reentry is required after the initial form submission. AI assists only in prefilling and validating – never in suggesting alternative trades or counterparties.
