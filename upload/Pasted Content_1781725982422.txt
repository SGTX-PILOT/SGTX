PART 3 – UNIVERSAL SHIPMENT TRACKING NUMBER (USTN) – FULL SPECIFICATION
3.0 Purpose & Design Philosophy
The Universal Shipment Tracking Number (USTN) is the single master identifier that binds every piece of data, every document, every payment, and
every physical movement of an SGTX trade transaction into one inseparable digital chain. It is the answer to the question: “How do we ensure that the
invoice seen by Customs is the same invoice seen by the tax authority, the shipping line, the bank, and the buyer – and that the payment matches it
exactly?”
The USTN is generated automatically at contract lock (singleshipment) or pershipment lock (multishipment). From that point forward, no document
can be created, no payment can be instructed, and no container can move without referencing this number. It is printed on the Bill of Lading,
embedded in the eInvoice XML, included in the ACID filing, written on the phytosanitary certificate, and used as the payment narrative in the Central
Bank’s Instant Payment Network.
Key properties:
• Globally unique – includes buyer and seller GTID suffixes, timestamp, and random.
• Deterministic – generated by an algorithm, not a central sequence (except the random part).
• Immutable – once generated, it never changes (though a shipment may be cancelled, the USTN remains as a historical record).
• Machinereadable and humanreadable – 42character alphanumeric (excluding I, O, 0, 1 in the random part).
• Mandatory – every SGTX document, API call, and payment reference must include the USTN.
AI assistance (nonmarketplace):
• When a user needs to reference a USTN (e.g., in a support query or dispute), the system autocompletes from a dropdown of recent USTNs the
user has access to – no suggestions from “similar trades of others”.
• The USTN QR code can be scanned by the mobile app, which then automatically opens the relevant Trade Command Center – no manual
typing.
• If a user manually types a USTN, the system validates the format in real time and, if valid, resolves it to a summary card (status, parties,
commodity) without needing to submit a form.

3.1.2 Generation Rules
The USTN is generated by the Contract Service when:
• Singleshipment contract: after mutual confirmation and SGTX fee payment (seller’s side pays).
• Multishipment contract: pershipment, after mutual confirmation for that specific shipment and payment of the pershipment SGTX fee.
Algorithm (Rust implementation, deterministic, no AI):
rust
use chrono::Utc;
use rand::Rng;
const ALPHABET: &[u8] = b"ABCDEFGHJKLMNPQRSTUVWXYZ23456789";
fn generate_ustn(buyer_gtid: &str, seller_gtid: &str) -> String {
let buyer_suffix = extract_suffix(buyer_gtid);
let seller_suffix = extract_suffix(seller_gtid);
let timestamp = Utc::now().format("%Y%m%d%H%M%S").to_string();
let mut rng = rand::thread_rng();
let random8: String = (0..8).map(|_| ALPHABET[rng.gen_range(0..ALPHABET.len())] as char).collect();
format!("SGTX-{}-{}-{}-{}", buyer_suffix, seller_suffix, timestamp, random8)
}
fn extract_suffix(gtid: &str) -> String {
let cleaned: String = gtid.chars().filter(|c| *c != '-').collect();
let len = cleaned.len();
cleaned[(len-6)..].to_string()
}
Why companyanchored? Prevents replay attacks across different counterparties. A USTN from trade A cannot be used to impersonate trade B
because the buyer/seller suffixes differ.
AI assistance for USTN generation: The user never sees the generation algorithm. The system automatically creates the USTN at the right moment
and prepopulates it into every document and API call. No user input required.

3.4 USTN in Documents – Mandatory Inclusion
Every document generated by or uploaded to SGTX must contain the USTN in a standardised location (e.g., header, footer, or QR code). This
includes:
• Commercial invoice (XML and PDF)
• Packing list
• Bill of lading (eBL or paper)
• Air waybill (courier)
• Phytosanitary certificate
• Health certificate
• Certificate of origin
• Laboratory test report
• QC inspection report
• Customs declaration (SAD)
• Payment instructions (PSP reference field)
• Logistics provider invoices
• Broker certification addendum
AI assistance for document generation: When a document is generated, the system automatically embeds the USTN and a QR code. No manual entry
required. If a user uploads a document, the system checks that the USTN is present (and matches the trade) before accepting it – if missing, it returns
a warning and suggests adding it (but does not autocorrect).
Physical marking: For paper documents (e.g., printed certificates of origin), the USTN is printed as both humanreadable text and a QR code. The QR
code encodes the full USTN URL: https://sgtx.io/ustn/SGTX-.... Scanning the QR code on a mobile device opens the Trade Command Center (readonly
view) – no login required for public verification (if the tenant has enabled public sharing).

3.6 USTN for MultiShipment Contracts
In a multishipment contract, a master contract ID exists but no master USTN. Each shipment receives its own USTN when it locks. The master
contract record in contracts table contains the schedule, and each contract_shipments row stores the shipmentspecific USTN.
Example – three shipments:
• Master contract: MC-20260415-001
• Shipment 1: SGTX-1397F3A-456ABC-20260415120000-A1B2C3D4
• Shipment 2: SGTX-1397F3A-456ABC-20260420080000-B2C3D4E5
• Shipment 3: SGTX-1397F3A-456ABC-20260425140000-C3D4E5F6
Each shipment’s USTN can be in a different lifecycle state (e.g., Shipment 1 delivered, Shipment 2 in transit, Shipment 3 locked). The buyer and seller
see all shipments in the Trade Command Center under the master contract.
AI assistance for multishipment: The Smart Inbox groups pending actions by shipment, with a clear label “Shipment 2 of 3”. The user can toggle
between shipments in the Trade Command Center via a dropdown that autocompletes from the list of USTNs under the master contract.
3.7 USTN for Distressed MicroContracts
When a seller declares distress on a portion of a shipment (e.g., 3 pallets of lemons), SGTX generates a microUSTN for the distressed lot. The
microUSTN follows the same format but links back to the original USTN via parent_ustn.
Example:
• Original USTN: SGTX-1397F3A-456ABC-20260415120000-A1B2C3D4
• MicroUSTN: SGTX-1397F3A-456ABC-20260420150000-D4E5F6G7
The microUSTN has its own lifecycle
(e.g., DISTRESS_SALE_PENDING → DISTRESS_MICROCONTRACT_LOCKED → DISTRESS_SALE_COMPLETED). It references the original
USTN in the parent_ustn field. All original documents are copied (with redacted pricing if confidential) to the microcontract.
AI assistance for distressed USTN: When a user views the original USTN, the system displays a banner: “This shipment has a distressed
microcontract (microUSTN ...). Click to view.” The link autocompletes to the microUSTN.
3.8 USTN in API Calls – Mandatory Reference
All SGTX API calls that create or modify traderelated entities must include the USTN (or microUSTN) in the request body or as a query parameter.
Examples:
• POST /v1/shipment/milestone/confirm → body: { "ustn": "...", "milestone": "LOADED" }
• POST /v1/broker/certify/{ustn}
• POST /v1/dispute/file → body: { "ustn": "...", "category": "QUALITY" }
• GET /v1/shipment/{ustn}
If an API call omits the USTN where required, the Governor returns a 400 error with a plainlanguage message: “Missing USTN parameter. Every
trade action must reference its shipment identifier.”
AI assistance for API consumers: The OpenAPI specification includes examples, and the interactive Swagger UI autocompletes USTN parameters
from a list of the user’s active USTNs (when the user is authenticated).
3.9 USTN & Blockchain Anchoring (Addon 6)
For highvalue or regulated shipments, the USTN master object’s hash (including all milestones, documents, and payment confirmations) is anchored
on a public blockchain (Ethereum mainnet or Polygon) using a batched Merkle root. The transaction ID is stored in blockchain_anchor.txid. Anyone
can verify the integrity of the USTN record by recomputing the hash and checking it against the anchored root. This provides courtgrade
nonrepudiation.
Verification endpoint: GET /v1/ustn/{ustn}/proof returns the Merkle proof and blockchain transaction details. The response includes a plainlanguage
explanation generated by Groq: “This USTN’s history is anchored on the Ethereum blockchain at transaction 0xabc... You can verify using any
Ethereum explorer.”
AI assistance for verification: The user clicks “Verify on Blockchain” in the Trade Command Center. The system checks the anchor and displays a
green badge if valid, or a red warning if the anchor is missing or inconsistent.
3.10 USTN for Analytics & Search
The USTN is indexed in PostgreSQL with a Btree index for exact lookups. Additionally, a fulltext search index is maintained on the USTN string (for
partial matches) and on the concatenated buyer/seller names and commodity descriptions. The Shared Shipments Vault uses this index for the global
search bar.
AI assistance for search: As the user types in the search bar, the system autocompletes with matching USTNs and also suggests filtering by status (e.g.,
“show all shipments with status DELIVERED”). The suggestions are based on the user’s own data, not on “popular searches of others”.

3.12 USTN QR Code & Physical Tagging
Every USTN is encoded as a QR code that can be printed on shipping labels, packing lists, and customs documents. The QR code contains:
• The full USTN string
• A URL to the public verification page: https://sgtx.io/verify/ustn/{ustn}
• A cryptographic signature (optional, for highvalue goods) that can be verified offline using the SGTX public key.
AI assistance for QR scanning: The SGTX mobile app scans the QR code and automatically opens the Trade Command Center (or the public
verification page). If the user is not logged in, the app prompts for login (or shows public information if enabled).
Offline verification: A receiver with no internet can scan the QR code, and the app uses a cached version of the SGTX public key to verify the
cryptographic signature, confirming that the USTN was issued by SGTX and has not been tampered with.

3B.1.2 Core Governance & Identity
• GTID format: SGTX-{COUNTRY_CODE}-{ENTITY_TYPE}-{SEQUENCE}-{CHECKSUM}
• Resolution endpoint: GET /v1/gtid/resolve returns public info (legal name, jurisdiction, trust score, KYB tier, sanctions clearance).
• Governor – Single entry point for every irreversible action. Enforces OPA policies + WasmEdge constitutional rules + AI consult (A1A3). Every
decision is logged via Loom (deterministic hash chain) and signed with Ed25519.
• Dualmode toggle – For TRD tenants with DUAL mode, header toggle switches between Buyer Dashboard (inbound) and Seller Dashboard
(outbound). Context stored in JWT.
3B.1.3 Common Shared Components (All Portals)
These components are available from the moment the tenant enters the portal after onboarding.
3B.1.3.1 Smart Inbox – with Recommended Actions Widget (Improvement #10)
Purpose: Default landing page for every authenticated user. Shows a prioritised action feed.
Components:
• Prioritybased list (High/Medium/Low) – each item shows USTN, category, deadline, action button.
• AIgenerated titles and descriptions – A1 (Groq → Ollama).
• Recommended Actions Widget – a compact box at the top of the inbox that displays the single next click for each active trade/financing/
distressed entity. Examples:
• “USTN SGTX-EG-...: Sign contract (1 click)”
• “USTN SGTX-VN-...: Pay Stage 1 (1 click)”
• “Financing #FR001: Submit bid (1 click)”
• AI Summary Card – Groq summarises today’s priorities.
Oneclick guarantee: From the Smart Inbox, the user can click any action button and directly execute the irreversible action (after Governor
validation). No intermediate screens.
Nonmarketplace: Items only appear for existing counterparties or obligations. Never suggests new relationships.
3B.1.3.2 Trade Command Center (TCC)
Purpose: Single page view for a USTN (or financing agreement / distressed microUSTN).
Layout:
• Persistent header (USTN badge, status, quick actions)
• Horizontal timeline (phases from initiation to settlement)
• Pending action panel – shows the single next action with a large button
• Summary cards: commercial, parties, shipment, documents, finances, risk, logistics, QC, multishipment schedule
• Activity feed (chronological events)
• Collaborative trade room (chat + task board)
Oneclick guarantee: The pending action panel always has exactly one primary button. Clicking it executes the next step.
3B.1.3.3 PlainLanguage Governor Decision Panel
Purpose: Explains any DENY or CONDITIONAL verdict in plain language with remediation links.
Content: Summary, condition checklist ( / ), action URLs, escalation hint, optional confidence/evidence.
Oneclick guarantee: Each condition has a direct action link (e.g., “Upload Certificate”). After resolving, the user clicks “Retry” – one click to resubmit
the original action.
3B.1.3.4 Shared Shipments Vault
Purpose: Paginated, filterable, sortable table of shipments (or financing agreements / distressed lots).
Features: Global search, filter chips, saved views, export (CSV/PDF), map view, realtime updates (NATS). Columns are rolespecific.
Oneclick guarantee: Clicking any USTN opens the TCC (one click). Export is one click.
3B.1.3.5 VoiceCommandButton
Technology: Vosk (offline) + HF Mixtral (intent extraction).
Capabilities: “Sign contract for USTN ...”, “Load pallet OR005”, “Approve settlement”, “Switch to Seller mode”.
Oneclick guarantee: Voice command executes the action after biometric verification – zero clicks.
3B.1.3.6 Customer Care Chatbot
Function: AIpowered support accessible from any portal. Can answer questions, perform actions on user’s behalf with PINbased impersonation,
escalate to human (VoIP callback).
Oneclick guarantee: “Chat” button opens the bot. User can speak or type a request; bot executes if possible.
3B.1.4 Internal Tenant Organization Graph
For large enterprises, tenant admins can create:
• Business units, departments, cost centres.
• Approval chains (e.g., “contracts >$100k require 2 managers”).
• Data scopes (hide cost components from warehouse staff).
Oneclick guarantee: Admin clicks “Add Approval Policy” → fills form → saves. Governor enforces.
3B.1.5 Tenant Lifecycle Engine
State

Oneclick guarantee: After completing Step 6, user clicks “Go Live” – one click to transition to VERIFIED.
3B.1.6 Network Feature (Saved Contacts)
Automatically saves counterparties after any interaction (trade, quote, message, distressed notification). AIenriched trust portraits, relationship health
scores, indirect connections.
Oneclick guarantee: “Add to Contacts” button (if not autosaved). No discovery – user must already know the GTID.
3B.1.7 Sandbox Environment
Isolated replica with synthetic data. User practices a full trade guided by tooltips.
Oneclick guarantee: “Reset Sandbox” – one click to wipe and restart.
3B.1.8 Governor & Loom (Background)
• Every irreversible action (including the “one clicks” above) passes through Governor.
• Each decision is signed, Loomhashed, and stored.
• Hourly chain verification ensures tamperproof audit.
