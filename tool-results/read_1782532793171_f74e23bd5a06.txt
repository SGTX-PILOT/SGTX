     1→10.0 Purpose & Design Philosophy
     2→
     3→International trade disputes are inevitable. Goods arrive damaged,
     4→payments are delayed, quality does not match the contract, certificates
     5→turn out to be fraudulent, or one party simply fails to perform. In the
     6→traditional paper‑based trade world, resolving these disputes is slow,
     7→expensive, and often inconclusive. Evidence is scattered across emails,
     8→WhatsApp messages, PDFs from different sources, and paper files in
     9→different countries.
    10→
    11→SGTX embeds a comprehensive dispute management system directly into the
    12→trade operating system. Because every document, payment, and logistic
    13→event for a shipment is already bound to the USTN and immutably
    14→recorded, SGTX can instantly surface the complete, cryptographically
    15→verifiable truth of the transaction. The dispute module is not a
    16→marketplace — it never suggests alternative counterparties or service
    17→providers. It provides a neutral, structured, AI‑assisted mediation
    18→environment that helps the existing parties resolve their disagreement
    19→efficiently.
    20→
    21→Key capabilities:
    22→
    23→-   Any breach — quality, delay, non‑payment, documentation fraud, cold
    24→    chain failure, service quality (broker, lab, QC) — can be raised as
    25→    a dispute.
    26→
    27→-   One‑click filing — buyer, seller, logistics provider, or financier
    28→    can file with voice or text.
    29→
    30→-   Evidence autocompiler — automatically pulls all USTN data, sensor
    31→    logs, QC overrides, broker certification logs, and causal analysis.
    32→
    33→-   Causal inference engine (Add‑on 3) — identifies root causes (e.g.,
    34→    "68% due to temperature excursion") and suggests fair settlement.
    35→
    36→-   Mediation log — structured, multi‑language negotiation with
    37→    AI‑generated proposals.
    38→
    39→-   Escalation to arbitration — auto‑prepares case files for ICC,
    40→    DIFC‑LCIA, CRCICA.
    41→
    42→-   SGTX fee dispute — separate workflow for disputing the platform's
    43→    fee calculation.
    44→
    45→-   Reputation score (Trade Reliability Index) — dynamic 0‑1000 score
    46→    for every tenant, updated after each dispute resolution, influencing
    47→    financing rates, inspection frequency, and trading privileges. The
    48→    score is private — only the tenant sees their own full breakdown;
    49→    counterparties see only a summarised trust badge (e.g., "Advanced
    50→    Trusted").

   136→10.2 Dispute Filing — Step‑by‑Step
   137→
   138→10.2.1 Manual Filing (Web or Mobile)
   139→
   140→Step 1 — Access USTN: User navigates to Trade Command Center for the
   141→relevant USTN (or shipment USTN for multi‑shipment, or financing
   142→agreement ID, or microUSTN for distressed). Clicks "Raise Dispute".
   143→
   144→Step 2 — Select Category: From dropdown (see 10.1.1). Category
   145→determines which evidence is auto‑compiled and which parties are
   146→notified.
   147→
   148→Step 3 — Describe Breach: Free‑text description (min 10 characters).
   149→System may pre‑fill based on detected anomalies.
   150→
   151→Step 4 — Attach Evidence: User uploads photos, PDFs, or references
   152→external reports. The system will already have auto‑compiled a base
   153→evidence package, but user can add more.
   154→
   155→Step 5 — Specify Remedy Sought: e.g., "Full refund of $100,000",
   156→"Partial refund of $10,000", "Replace damaged pallets", "Extend payment
   157→terms by 30 days".
   158→
   159→Step 6 — Submit: Governor validates that the user has permission to file
   160→a dispute for that USTN. If ALLOW, dispute is created with
   161→unique dispute_id. USTN status becomes DISPUTED. All pending payments
   162→are frozen, and container release (if still at port) is blocked.
   163→
   164→Voice‑initiated filing (mobile app):
   165→
   166→text
   167→
   168→User speaks: "File dispute for USTN SGTX-... The oranges arrived with
   169→mould. I want $2,000 refund."
   170→
   171→Vosk transcribes → HF Mixtral extracts USTN, category (QUALITY), amount
   172→→ pre‑fills form.
   173→
   174→User confirms → dispute filed.
   175→
   176→One‑click: Click "Submit Dispute" (1) → dispute created.
   177→
   178→AI Authority: A1 for voice transcription and intent extraction; A4 for
   179→Governor validation.
   180→
   181→10.2.2 Automatic Advisory Dispute (System‑Triggered)
   182→
   183→System detects anomaly — e.g., temperature deviation >5°C for >2 hours.
   184→Smart Inbox item appears: "Potential cold chain failure detected on USTN
   185→... Click to file a dispute proactively." Buyer can accept (pre‑filled
   186→form) or ignore. The system never automatically files; it only suggests.
   187→
   188→AI Authority: A2 for anomaly detection (LSTM); A1 for advisory message.

   354→10.4 Causal Inference Engine (Add‑on 3) — Root Cause Analysis
   355→
   356→10.4.1 Trigger & Model
   357→
   358→When a dispute is filed, the causal inference engine (A2, DoWhy +
   359→EconML) is triggered asynchronously. It analyses:
   360→
   361→-   Timeline of milestones (delays between expected and actual)
   362→
   363→-   Sensor data (temperature, humidity, shock)
   364→
   365→-   Weather and port congestion (from RIA)
   366→
   367→-   Carrier performance history (on‑time delivery, damage claims)
   368→
   369→-   QC override patterns (frequency, type of overrides)
   370→
   371→-   Broker certification history (accuracy, rejections)
   372→
   373→Methodology: DoWhy builds a causal graph (DAG) based on domain
   374→knowledge; EconML estimates the Average Treatment Effect (ATE) and
   375→contribution of each factor using double‑ML.
   376→
   377→10.4.2 Output
   378→
   379→A JSON object with root causes and contribution percentages, stored
   380→in causal_attribution. Groq generates a plain‑language summary added to
   381→the evidence package and displayed in the mediation log.

   639→10.7 Smart FeeLock Management (Freeze & Partial Release)
   640→
   641→10.7.1 Dispute Filing → FeeLock Freeze
   642→
   643→When a dispute is filed:
   644→
   645→-   The Governor freezes the affected FeeLock(s).
   646→
   647→-   Government fees already paid are not refundable (by law).
   648→
   649→-   Pending fee payments are frozen.
   650→
   651→-   If the dispute involves only part of a shipment (e.g., 3 of 22
   652→    pallets), the system can partially release the undisputed portion
   653→    for settlement.
   654→
   655→10.7.2 Partial Release Criteria
   656→
   657→  -----------------------------------------------------------------------
   658→  Criteria              Requirement
   659→  --------------------- -------------------------------------------------
   660→  Separability          The undisputed portion must be clearly separable
   661→                        (e.g., by pallet).
   662→
   663→  Governor approval     Requires Governor decision with A3 approval
   664→                        (human review).
   665→
   666→  No impact on disputed Release of undisputed portion must not affect the
   667→  portion               disputed portion's value.
   668→
   669→  Both parties' consent Optional — if not, requires Platform Governance
   670→                        Authority approval.
   671→  -----------------------------------------------------------------------
   672→
   673→One‑click: If partial release is proposed, the non‑disputing party
   674→clicks "Approve Release" (1). Governor releases the portion.
   675→
   676→AI Authority: A3 for partial release approval (human escalation); A4 for

   679→10.8 Document Authenticity Check (A2)
   680→
   681→10.8.1 Purpose
   682→
   683→If a party submits new evidence that contradicts previously uploaded
   684→documents, the document-authenticity agent (HF Donut + metadata
   685→analysis) cross‑checks:
   686→
   687→-   Metadata (dates, author, digital signatures)
   688→
   689→-   Consistency of issuing body with original document
   690→
   691→-   Any signs of tampering (hash comparison, pixel‑level analysis)

   763→10.10 Predictive Dispute Outcome (A2, XGBoost)
   764→
   765→10.10.1 Trigger & Model
   766→
   767→Trigger: After evidence is compiled, the system runs a predictive model
   768→trained on past SGTX dispute outcomes.
   769→
   770→Input features:
   771→
   772→-   Dispute type, commodity, incoterm, ports
   773→
   774→-   Party trust scores and dispute history
   775→

   777→    destination damage)
   778→
   779→-   Contractual strength of the complaining clause
   780→
   781→-   QC override patterns (frequency, reasons)
   782→
   783→-   Causal analysis output (if available)

   786→

   788→
   789→-   Predicted damage amount (range)
   790→
   791→-   Confidence interval

   793→-   Groq‑generated neutral, plain‑language summary
   794→

   796→"Estimated probability of buyer winning: 78%. Typical award range:

   800→parties see the same prediction.
