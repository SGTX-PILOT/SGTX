   202→13.1.27 Row‑Level Security (RLS) Policies
   203→
   204→sql
   205→
   206→-- Enable RLS on all tables
   207→
   208→ALTER TABLE tenants ENABLE ROW LEVEL SECURITY;
   209→
   210→ALTER TABLE employees ENABLE ROW LEVEL SECURITY;
   211→
   212→ALTER TABLE trade_requests ENABLE ROW LEVEL SECURITY;
   213→
   214→ALTER TABLE shipments ENABLE ROW LEVEL SECURITY;
   215→
   216→ALTER TABLE contracts ENABLE ROW LEVEL SECURITY;
   217→
   218→ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
   219→
   220→ALTER TABLE dispute ENABLE ROW LEVEL SECURITY;
   221→
   222→-- Tenants RLS
   223→
   224→CREATE POLICY tenants_tenant_isolation ON tenants
   225→
   226→USING (gtid = current_setting('app.current_tenant_gtid')::text OR
   227→
   228→EXISTS (SELECT 1 FROM employees WHERE tenant_id = id AND employees.id =
   229→current_setting('app.current_employee_id')::uuid));
   230→
   231→-- Employees RLS
   232→
   233→CREATE POLICY employees_tenant_isolation ON employees
   234→
   235→USING (tenant_id = current_setting('app.current_tenant_id')::uuid);
   236→
   237→-- Trade requests RLS
   238→
   239→CREATE POLICY trade_requests_tenant_isolation ON trade_requests
   240→
   241→USING (buyer_tenant_id = current_setting('app.current_tenant_id')::uuid
   242→OR
   243→
   244→seller_tenant_id = current_setting('app.current_tenant_id')::uuid);
   245→
   246→-- Shipments RLS
   247→
   248→CREATE POLICY shipments_tenant_isolation ON shipments
   249→
   250→USING (exporter_gtid = current_setting('app.current_tenant_gtid')::text
   251→OR
   252→
   253→importer_gtid = current_setting('app.current_tenant_gtid')::text OR
   254→
   255→EXISTS (SELECT 1 FROM service_quotations WHERE ustn = shipments.ustn AND
   256→provider_gtid = current_setting('app.current_tenant_gtid')::text));
   257→
   258→-- Documents RLS
   259→
   260→CREATE POLICY documents_tenant_isolation ON documents
   261→
   262→USING (tenant_id = current_setting('app.current_tenant_id')::uuid OR
   263→
   264→EXISTS (SELECT 1 FROM shipments WHERE ustn = documents.ustn AND
   265→
   266→(exporter_gtid = current_setting('app.current_tenant_gtid')::text OR
   267→
   268→importer_gtid = current_setting('app.current_tenant_gtid')::text)));
   269→
   270→-- Disputes RLS
   271→
   272→CREATE POLICY disputes_tenant_isolation ON disputes
   273→
   274→USING (filing_party_gtid =
   275→current_setting('app.current_tenant_gtid')::text OR
   276→
   277→EXISTS (SELECT 1 FROM shipments WHERE ustn = disputes.ustn AND
   278→
   279→(exporter_gtid = current_setting('app.current_tenant_gtid')::text OR
   280→
   281→importer_gtid = current_setting('app.current_tenant_gtid')::text)));

   766→14.0 Purpose & Design Philosophy
   767→
   768→The SGTX platform handles sensitive trade data, financial transactions,
   769→and cryptographic identities across multiple jurisdictions. A robust
   770→security model is not optional — it is a constitutional requirement.
   771→This part defines the comprehensive threat model for the SGTX platform
   772→using industry‑standard frameworks:
   773→
   774→-   STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure,
   775→    Denial of Service, Elevation of Privilege) — per component, per
   776→    trust boundary.
   777→
   778→-   MITRE ATT&CK — adversary tactics, techniques, and procedures (TTPs)
   779→    relevant to trade platforms.
   780→
   781→All mitigations are zero‑cost, built on open‑source tools (OPA,
   782→WasmEdge, Cilium, Falco, etc.) and free threat intelligence feeds. AI
   783→(Groq, Hugging Face) is used for advisory purposes — e.g., summarising
   784→threat findings, generating post‑mortems, and suggesting remediation
   785→steps. Never autonomous blocking (A5 forbidden).
   786→

   801→
   802→Key principles (non‑marketplace, orchestration‑only):
   803→
   804→-   Zero‑trust architecture — no implicit trust; every request is
   805→    authenticated, authorised, and encrypted.
   806→
   807→-   Defence in depth — multiple layers of control (network, application,
   808→    data, constitutional).
   809→
   810→-   Immutable audit — every security‑relevant event is logged immutably
   811→    via Loom.
   812→

   814→    pentests, daily vulnerability scans.
   815→

  1004→14.2.1 Example — Spoofing Mitigation for GTID
  1005→
  1006→An attacker cannot impersonate a tenant because every request requires a
  1007→JWT signed with the tenant's Ed25519 private key. ZITADEL WebAuthn
  1008→enforces biometric liveness for high‑value actions
  1009→(e.g., contract.sign). The JWT is short‑lived (15 minutes) and rotated
  1010→via refresh token.
  1011→
  1012→Attack Scenario: Attacker steals a JWT token.
  1013→Mitigation: JWT has short TTL (15 min). Refresh token requires biometric
  1014→verification. All API calls validated against device registry (Part
  1015→1.14).
  1016→
  1017→14.2.2 Example — Tampering Mitigation for Loom
  1018→
  1019→An attacker who gains write access to the governor_decisions table
  1020→cannot modify a past decision because the Loom hash chain would break.
  1021→The hourly verifier (audit-chain-verifier) detects any inconsistency and
  1022→triggers a P0 incident.
  1023→
  1024→Attack Scenario: Attacker modifies a Governor decision.
  1025→Mitigation: Loom hash chain breaks. Hourly verifier detects mismatch →
  1026→P0 incident → Governor blocks new decisions until restored from WAL.
  1027→
  1028→14.2.3 Example — Information Disclosure Mitigation for RLS
  1029→
  1030→Row‑Level Security ensures that a tenant can only see their own data.
  1031→The Governor sets app.current_tenant_gtid in the session context, and
  1032→PostgreSQL RLS enforces it at the database level. Even if an attacker
  1033→bypasses the application layer, they cannot access other tenants' data.
  1034→
  1035→Attack Scenario: Attacker crafts SQL query directly against PostgreSQL.
  1036→Mitigation: PostgreSQL RLS denies access if app.current_tenant_gtid is
  1037→not set or does not match. The Governor is the only service that can set
  1038→this variable.
