PART 4 — DYNAMIC PRODUCT-AWARE REQUEST FORM

4.0 Purpose & Design Philosophy

The Dynamic Product-Aware Request Form is the entry point for every
trade. It uses AI‑driven dynamic schema generation to adapt the form in
real time based on the selected product, origin, destination, port, and
any special requirements (e.g., cold treatment, fumigation, specific
certificates). The buyer never needs to research regulations manually —
the system pre‑populates the required fields, documents, and lab tests.
Moreover, the form dynamically generates the exact fields needed for the
packing list — such as pallet size, number of pallets, cartons per
pallet, layer arrangement, and packaging details — tailored to the
specific commodity and its handling requirements.

Key principles (non‑marketplace):

-   One source of truth — all structured container and commodity data
    stored in trade_requests.parsed_specs JSONB; reused throughout the
    workflow.

-   AI dynamically builds the form — required documents,
    commodity‑specific fields, lab tests, special conditions, and
    packing fields are added automatically based on the product and
    route.

-   AI never suggests "you might also want to export to X" or "other
    buyers used Y" .

-   Auto‑detection of special procedures — e.g., if the destination
    country or port requires cold treatment, fumigation, or pre‑cooling,
    the system adds the necessary fields and document requirements.

-   Dynamic packing specification — for each commodity, the system asks
    for pallet dimensions (EUR, ISO, custom), number of pallets, cartons
    per pallet, layers, stacking height, and packaging type — all
    derived from product‑specific defaults and RIA data.

-   Two‑way smart product/HS code resolution — entering a product name
    auto‑fills the HS code; entering an HS code auto‑fills the product
    name.

-   Express Mode (optional) — users who prefer natural language can
    describe their trade in plain English; AI parses and extracts
    structured data.

-   Multi‑commodity, multi‑container — supports unlimited containers and
    unlimited commodities per container.

-   Multi‑shipment ready — optional schedule builder for future
    deliveries.

-   Draft auto‑save — every 30 seconds, resumes via Smart Inbox.

-   Incoterm selection — buyer selects incoterm at the start, which
    determines logistics responsibilities later.

The form is buyer‑facing (Trader Portal, Buyer mode) but the data is
stored and reused throughout — for seller's packing, customs
declaration, invoice generation, and financing. No data re‑entry across
phases.

4.1.3 AI Assistance for RIA Data

When a buyer selects a product, the system automatically fetches and
displays relevant:

-   Packing defaults (pallet type, cartons per pallet, net weight,
    stacking height)

-   Special procedures (cold treatment, fumigation, pre‑cooling)

-   Treatment requirements (temperature, duration, accepted facilities)

-   Document mandates (phyto, health, COO, cold chain log)

-   Lab tests required (analytes with MRLs)

The buyer does not need to research these manually — but the system
never says "other buyers exported to this country used broker X".

AI Authority: A2 (HF local for scraping and NLP, Groq for summarisation)

4.2 Incoterm Selection (Buyer Responsibility)

4.2.1 Location & Behaviour

Location: Immediately after seller selection, before container entry.

The buyer selects an incoterm from a dropdown (Incoterms 2020). The
selected incoterm is stored in trade_requests.parsed_specs.incoterm and
determines:

-   Which logistics services are the seller's responsibility vs. the
    buyer's responsibility.

-   Which costs must be included in the seller's quote (e.g., for CFR,
    seller must include sea freight; for FOB, seller only up to loading
    on vessel).

-   Default SGTX fee payer (always seller's side, but incoterm affects
    trade value calculation).

4.2.3 Auto‑Configuration

Immediately after incoterm selection:

1.  The system stores the incoterm
    in trade_requests.parsed_specs.incoterm.

2.  It pre‑populates the seller's mandatory logistics services list
    (visible later in Phase 2). For example, if buyer selects CFR, the
    seller will see Ocean Freight as mandatory. If FOB, ocean freight is
    disabled.

3.  A plain‑language summary of responsibilities (A1, Groq) is shown to
    both buyer and seller:

    -   "You (buyer) are responsible for main carriage. Seller is
        responsible for export clearance and delivery to port."

4.  The incoterm also influences the SGTX fee calculation (1.5% of total
    trade value, but trade value defined per incoterm).

4.2.4 Incoterm Engine Validation

Governance: WasmEdge incoterms_engine.wasm validates that later
logistics cost entries match the selected incoterm (e.g., ocean freight
cannot be added for FOB). If a mismatch is detected during quote
submission, the Governor returns a CONDITIONAL verdict with a Decision
Panel explanation.

One‑click: Buyer selects incoterm from dropdown → system applies rules
instantly. No additional click needed.

AI Authority: A1 — plain‑language explanation (Groq); A4 — incoterm
validation against jurisdiction (WasmEdge).

4.3 Product Form Agent (A2) — Dynamic JSON Schema Generation

4.3.1 Trigger & Process

When the buyer selects a product (by typing a product name or HS code),
the frontend calls the Product Form Agent (via ai-agent-orchestrator).
The agent:

1.  Queries the RIA vector database for all relevant regulations for
    that product, origin, destination, and port — including:

    -   Required documents (phyto, health, COO, EUR1, cold chain log,
        treatment certificates).

    -   Special procedures (cold treatment, fumigation, irradiation,
        pre‑cooling).

    -   Product‑specific dynamic fields (variety, grade, brix, size
        range, etc.).

    -   Packing defaults — pallet type, cartons per pallet, net weight
        per carton, stacking height, packaging types.

    -   Lab tests required (analytes with MRLs).

2.  Calls Groq (fallback Ollama) with a prompt that includes the
    retrieved context.

3.  Returns a JSON schema that defines:

    -   required_documents (with auto_generate flag and trigger if
        applicable)

    -   dynamic_fields (type, options, min, max, mandatory, default) —
        includes product‑specific attributes and packing fields

    -   lab_tests_required (analyte, MRL, unit)

    -   special_conditions (e.g., "Cold treatment required", "Fumigation
        required", "ISPM 15 required")

    -   treatment_details (e.g., { "type": "cold_treatment",
        "temperature_c": -0.5, "duration_days": 14,
        "certificate_required": true })

    -   packing_defaults (e.g., { "pallet_type": "EUR",
        "cartons_per_pallet": 40, "net_weight_per_carton_kg": 10,
        "stacking_layers": 5, "max_pallets_per_container": 22 })

4.4 Structured Container & Commodity Entry (Dynamic Form)

4.4.1 Form Overview

The form is fully dynamic — fields appear and disappear based on the
product and destination requirements. The buyer can specify:

-   Number of containers (default 1, max 50) — each container gets a
    tab.

-   Per‑container fields — country of origin, destination country, port
    of discharge, palletized? (Yes/No), pallet size, destination

-   Commodities within container (unlimited) — commodity type, product

    packing fields, treatment details section, packaging, number of

Two‑way auto‑synchronisation workflow:

1.  Buyer selects Commodity Type → system fetches filtered dropdown of
    all products belonging to that type (from HS database, updated by
    RIA).

2.  Buyer selects product from dropdown → system automatically:

    -   Fills the HS code (6 or 10 digits) into a read‑only or editable
        field (can be overridden but warns).

    -   Triggers the Product Form Agent (A2) to generate dynamic
        specifications.

3.  Buyer types HS code directly (with autocomplete suggestions) → upon
    selection, system:

    -   Fills the product name (from the HS database).

    -   Filters the product dropdown to match that HS code.

    -   Triggers the same Product Form Agent.

4.  Buyer types free‑text product name (not in dropdown) → system:

    -   Attempts to match it to an HS code via AI (A2, HF local).

    -   Suggests the closest match with confidence score.

    -   Buyer can accept or override.

    -   If accepted, triggers Product Form Agent.

5.  AI suggestion from buyer's history — as buyer types, system shows
    previously used products (from buyer's own trade history) with a
    "recent" badge. Never suggests "popular" or "other buyers" products.

Non‑marketplace safeguard: The dropdown is filtered by commodity type
and buyer's saved products, not by "most popular". AI only assists based
on public data and buyer's own history.

4.4.6 Express Mode (Free‑Text AI Parsing, Optional)

Purpose: For users who prefer natural language over structured forms.

Toggle: "Use AI Express" at the top of the New Trade Request form. When
enabled, the structured form is hidden and replaced with a single large
text area.

Express Mode Interface:

-   Text area (minimum height 200px) with placeholder:
    "Describe your trade in plain English. Example: I need 20,000 kg of
    Valencia oranges from Vietnam, CFR Alexandria, packed in 10 kg
    cartons, 22 pallets. Also 5,376 kg of lemons in mesh bags, 14
    pallets. Two containers, second container to Port Said."

-   Microphone icon for voice input (speech‑to‑text via Vosk offline or
    Web Speech API, with fallback).

-   "Parse" button that triggers the AI Intent Parser (A2, Hugging Face
    local primary, Ollama fallback).

Processing:

1.  System sends the raw text to the Intent Parser agent.

2.  Agent extracts: number of containers, per‑container
    origin/destination/port, commodities, HS codes (if inferable),
    quantities, packaging, pallet counts, incoterm, and multi‑shipment
    schedule.

3.  Extracted data is displayed in a preview panel showing the
    structured form that would be generated.

4.  For each extracted field, a confidence score (0‑100) is shown.
    Fields with confidence below 80% are highlighted in amber with a
    note: "Please verify or correct."

5.  The buyer can edit any extracted field directly in the preview.

6.  Once confirmed, the system populates the full structured form and
    the buyer proceeds to standard validation and submission.

Fallback and Error Handling:

-   If AI cannot parse the text (confidence <50% for critical fields),
    system displays: "We could not fully understand your request. Please
    try rephrasing or switch back to the structured form."

-   A "Switch to Structured Form" button is always visible.

Voice Input Enhancement:

-   Clicking the microphone opens a voice recording modal. Vosk
    (offline) transcribes; then passes to Intent Parser.

Governance (G1U2, G1U3): Express Mode is advisory only. Governor does
not accept a trade request based solely on Express Mode parsing; buyer
must review and confirm extracted data before submission.

4.10 Draft Auto‑Save & Recovery

4.10.1 Auto‑Save Mechanism

Every 30 seconds (debounced), the current form state is saved as
a draft in the trade_requests table with status = 'DRAFT'. The draft
includes:

-   parsed_specs (partial or complete, including packing defaults and
    treatment details)

-   multi_shipment_schedule (if any)

-   updated_at timestamp

4.10.2 Resume Workflow

-   When the buyer returns to the portal, the Smart Inbox shows a
    low‑priority item (score 30): "Continue draft trade request from
    [date]".

-   Clicking it opens the form with the saved data.

-   Drafts expire after 14 days of inactivity; reminders at 11 and 13
    days.

-   Expired drafts can be restored via Company Admin → Drafts (admin
    only).

Backend endpoint for draft saving: POST /v1/trade/request/draft with {
"trade_request_id": "...", "parsed_specs": {...} }. Governor validates
that the buyer has permission to edit the draft.

AI Authority: None (rule‑based auto‑save).
