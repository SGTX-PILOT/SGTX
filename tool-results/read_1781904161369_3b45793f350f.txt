   487→   766→14.0 Purpose & Design Philosophy
   488→   767→
   489→   768→The SGTX platform handles sensitive trade data, financial transactions,
   490→   769→and cryptographic identities across multiple jurisdictions. A robust
   491→   770→security model is not optional — it is a constitutional requirement.
   492→   771→This part defines the comprehensive threat model for the SGTX platform
   493→   772→using industry‑standard frameworks:
   494→   773→
   495→   774→-   STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure,
   496→   775→    Denial of Service, Elevation of Privilege) — per component, per
   497→   776→    trust boundary.
   498→   777→
   499→   778→-   MITRE ATT&CK — adversary tactics, techniques, and procedures (TTPs)
   500→   779→    relevant to trade platforms.
   501→   780→
   502→   781→All mitigations are zero‑cost, built on open‑source tools (OPA,
   503→   782→WasmEdge, Cilium, Falco, etc.) and free threat intelligence feeds. AI
   504→   783→(Groq, Hugging Face) is used for advisory purposes — e.g., summarising
   505→   784→threat findings, generating post‑mortems, and suggesting remediation
   506→   785→steps. Never autonomous blocking (A5 forbidden).
   507→   786→
   508→   787→AI Integration in Part 14:

   517→   796→  Ollama)           log analysis
   518→   797→

   520→   799→  WasmEdge)         limiting, constitutional rules)

   522→   801→
   523→   802→Key principles (non‑marketplace, orchestration‑only):
   524→   803→
   525→   804→-   Zero‑trust architecture — no implicit trust; every request is
   526→   805→    authenticated, authorised, and encrypted.
   527→   806→
   528→   807→-   Defence in depth — multiple layers of control (network, application,
   529→   808→    data, constitutional).
   530→   809→
   531→   810→-   Immutable audit — every security‑relevant event is logged immutably
   532→   811→    via Loom.
   533→   812→

   725→  1004→14.2.1 Example — Spoofing Mitigation for GTID
   726→  1005→
   727→  1006→An attacker cannot impersonate a tenant because every request requires a
   728→  1007→JWT signed with the tenant's Ed25519 private key. ZITADEL WebAuthn
   729→  1008→enforces biometric liveness for high‑value actions
   730→  1009→(e.g., contract.sign). The JWT is short‑lived (15 minutes) and rotated
   731→  1010→via refresh token.
   732→  1011→
   733→  1012→Attack Scenario: Attacker steals a JWT token.
   734→  1013→Mitigation: JWT has short TTL (15 min). Refresh token requires biometric
   735→  1014→verification. All API calls validated against device registry (Part
   736→  1015→1.14).
   737→  1016→
   738→  1017→14.2.2 Example — Tampering Mitigation for Loom
   739→  1018→
   740→  1019→An attacker who gains write access to the governor_decisions table
   741→  1020→cannot modify a past decision because the Loom hash chain would break.
   742→  1021→The hourly verifier (audit-chain-verifier) detects any inconsistency and
   743→  1022→triggers a P0 incident.
   744→  1023→
   745→  1024→Attack Scenario: Attacker modifies a Governor decision.
   746→  1025→Mitigation: Loom hash chain breaks. Hourly verifier detects mismatch →
   747→  1026→P0 incident → Governor blocks new decisions until restored from WAL.
   748→  1027→
   749→  1028→14.2.3 Example — Information Disclosure Mitigation for RLS
   750→  1029→
   751→  1030→Row‑Level Security ensures that a tenant can only see their own data.
   752→  1031→The Governor sets app.current_tenant_gtid in the session context, and
   753→  1032→PostgreSQL RLS enforces it at the database level. Even if an attacker
   754→  1033→bypasses the application layer, they cannot access other tenants' data.
