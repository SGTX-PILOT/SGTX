     1→7.0 Purpose & Design Philosophy
     2→
     3→SGTX is not a replacement for government systems — it is
     4→an orchestration layer that automates data submission to the four
     5→mandatory government APIs: Nafeza (Customs Single Window), CargoX (ACI
     6→Blockchain Platform), ETA (e‑Invoice), and Central Bank of Egypt
     7→(CBE) (payment & FX). Additionally, SGTX enables direct bank
     8→integration for trade principal settlement, allowing banks to reconcile
     9→payments without SGTX ever holding funds.
    10→
    11→Key Principles:
    12→
    13→-   Non‑custodial by design — SGTX never holds trade principal or fee
    14→    funds. It only instructs PSPs or provides reconciliation files to
    15→    banks.
    16→
    17→-   One‑click orchestration — After the user clicks "Pay Stage 1" or
    18→    "Settle Payment", SGTX triggers all government API calls in the
    19→    correct sequence, based on payment confirmation webhooks.
    20→
    21→-   Bank‑friendly reconciliation — SGTX generates USTN‑tagged settlement
    22→    instructions and provides APIs for banks to pull reconciliation data
    23→    (CSV, MT940, ISO 20022). Banks do not need to integrate with each
    24→    government API — they only need to receive instructions from SGTX
    25→    (or from PSPs) and confirm settlements.
    26→
    27→-   No new licence required — SGTX is not a bank; it merely provides
    28→    data. The actual movement of funds occurs between bank accounts via
    29→    PSPs or direct bank transfers.

   124→7.2 Nafeza Integration (Customs Single Window)
   125→
   126→7.2.1 Overview
   127→
   128→Nafeza is the national single window for trade. SGTX submits the Single
   129→Administrative Document (SAD) and requests ancillary certificates
   130→(phytosanitary, health, certificate of origin, EUR.1). SGTX can file
   131→directly using:
   132→
   133→-   Exporter's delegated authority — exporter authorises SGTX to file on
   134→    their behalf (consent stored in tenant profile).
   135→
   136→-   SGTX's own broker license — platform acts as a licensed customs
   137→    broker.
   138→
   139→-   Optional broker certification — if the seller has selected a customs
   140→    broker for certification, the broker reviews the AI‑generated SAD
   141→    and clicks "Certify"; then SGTX submits the SAD under the broker's
   142→    digital seal.
   143→
   144→Legal basis: Egyptian Customs Law No. 207 of 2020, Article 51.
   145→
   146→7.2.2 API Endpoint & Authentication
   147→
   148→  --------------------------------------------------------------------------
   149→  Parameter        Value
   150→  ---------------- ---------------------------------------------------------
   151→  Endpoint         https://b2g.nafeza.gov.eg/api/v2/declaration
   152→  (Production)     
   153→
   154→  Authentication   Mutual TLS (mTLS) with the filer's Egypt Trust e‑Seal
   155→                   certificate
   156→
   157→  Headers          Content-Type: application/json, X-Request-ID (UUID for
   158→                   idempotency), X-USTN (custom header for correlation)
   159→
   160→  Certificate      For direct filing: exporter's certificate (stored
   161→                   encrypted, accessed via HSM). For broker‑certified
   162→                   filing: broker's certificate.
   163→  --------------------------------------------------------------------------
   164→
   165→One‑click integration: No user action — certificate management is
   166→automatic.

   466→7.5 Direct Bank Integration — Non‑Custodial Settlement
   467→
   468→7.5.1 Philosophy
   469→
   470→SGTX is not a payment service provider and never holds funds. For trade
   471→principal settlement (buyer → seller), SGTX can either:
   472→
   473→-   Use PSPs (Fawry, PayMob, CBE IPN) with split capabilities, or
   474→
   475→-   Provide bank‑to‑bank settlement instructions directly. Banks
   476→    integrate with SGTX via API to receive reconciliation data, not to
   477→    move funds.
   478→
   479→How it works:
   480→
   481→1.  Buyer confirms delivery → SGTX generates a settlement
   482→    instruction containing buyer IBAN, seller IBAN, amount, currency,
   483→    USTN.
   484→
   485→2.  The buyer's bank (or the buyer themselves) initiates the transfer
   486→    (via their online banking, not via SGTX).
   487→
   488→3.  The buyer's bank sends a payment confirmation (MT103, ISO 20022
   489→    pacs.008) to the seller's bank.
   490→
   491→4.  SGTX reconciles the payment by matching the USTN reference from the
   492→    bank statement. SGTX does not initiate the transfer — the bank does.
   493→
   494→Bank onboarding: Any bank can register as a BANK tenant type (sub‑type
   495→of FIN). They provide their IBAN prefix, BIC, and API endpoint for
   496→receiving instructions (optional). SGTX then pushes settlement
   497→instructions to the bank's system (if supported) or the bank pulls them.
   498→

   601→
   602→  -------------------------------------------------------------------------

   605→  Fawry     Card, wallet, kiosk           ✅                ✅

   607→  PayMob    Card, wallet                  ✅                ✅

   617→7.7 Idempotency Key Standard for External Calls
   618→
   619→7.7.1 Purpose
   620→
   621→Prevent duplicate external API calls (e.g., double declaration
   622→submissions, double payment charges) by enforcing a standard idempotency
   623→key for all outgoing requests.
   624→
   625→7.7.2 Format
   626→
   627→text
   628→
   629→idempotency_key = SHA256( request_body_canonical +
   630→timestamp_utc_rounded_to_second )
   631→
   632→Where:
   633→
   634→-   request_body_canonical is the JSON request body serialised with JCS
   635→    (RFC 8785).
   636→
   637→-   timestamp_utc_rounded_to_second is the current UTC time truncated to
   638→    the nearest second (ISO 8601 format: YYYY-MM-DDTHH:MM:SSZ).
   639→
   640→Example:
   641→
   642→text
   643→
   644→request_body_canonical =
   645→'{"ustn":"SGTX-1397F3A-456ABC-20260415120000-A1B2C3D4","container":"MEDU1234567"}'
   646→
   647→timestamp = '2026-06-10T14:35:22Z'
   648→
   649→idempotency_key =
   650→SHA256('{"ustn":"SGTX-1397F3A-456ABC-20260415120000-A1B2C3D4","container":"MEDU1234567"}' +
   651→'2026-06-10T14:35:22Z')
   652→
   653→= 'a1b2c3d4e5f6...'
   654→
   655→7.7.3 Usage
   656→
   657→For every external API call (Nafeza, CargoX, ETA, PSPs, etc.), SGTX
   658→includes the idempotency key in the request headers:
   659→
   660→text
   661→
   662→X-Idempotency-Key: a1b2c3d4e5f6...
   663→
   664→7.7.4 Retry Behaviour
   665→
   666→-   If the external API returns a 5xx error, SGTX retries with the same
   667→    idempotency key.
   668→
   669→-   The external API (or SGTX's own wrapper) must store the key and
   670→    response for at least 24 hours, returning the same response on
   671→    duplicate keys (idempotent behaviour).
   672→
   673→-   For PSPs that do not support idempotency keys, SGTX adds a unique
   674→    UUID in the payment reference field as a fallback.
