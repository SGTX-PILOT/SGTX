     1→PART 19 — TRADE MEMORY LAYER & PREDICTIVE TRADE INSIGHTS
     2→
     3→19.0 Purpose & Design Philosophy
     4→
     5→The Trade Memory Layer is the long‑term, structured knowledge base of
     6→every trade event that occurs on the SGTX platform. Unlike raw audit
     7→logs (which are technical and access‑controlled), Trade Memory
     8→captures semantic, anonymised facts about delays, disputes,
     9→documentation failures, customs issues, financing outcomes, and
    10→logistics performance. This data is used exclusively for:
    11→
    12→-   Pattern detection — identifying recurring failure modes and
    13→    bottlenecks.
    14→
    15→-   Predictive analytics — forecasting risks and outcomes for active
    16→    trades.
    17→
    18→-   AI model training (federated learning) — improving fraud detection,
    19→    credit scoring, and margin estimation without exposing raw data.
    20→
    21→-   Strategic advisory — providing anonymised benchmarks and "what‑if"
    22→    insights to platform governance and participating tenants (with
    23→    consent).
    24→
    25→All stored events are anonymised before retention: original GTIDs are
    26→replaced with persistent, non‑reversible anonymous IDs. Raw event data
    27→remains in the audit log (subject to Part 18 retention rules). The Trade
    28→Memory Layer is never used to recommend counterparties, rank service
    29→providers, or violate non‑marketplace principles.
    30→
    31→Key principles (non‑marketplace, sovereign):
    32→
    33→-   Anonymisation first — no personal or commercial data is stored in
    34→    raw form.
    35→
    36→-   Opt‑in contribution — tenants control whether their data contributes
    37→    to the memory layer.
    38→
    39→-   Privacy‑preserving analytics — all aggregates use differential
    40→    privacy (ε=0.1).
    41→
    42→-   Federated learning ready — data can be used for cross‑node model
    43→    training without sharing raw events.
    44→
    45→-   No unsolicited recommendations — insights are advisory only and
    46→    never used to suggest counterparties.

   257→19.2 Anonymisation & Privacy
   258→
   259→19.2.1 Anonymisation Process
   260→
   261→Before any event is written to trade_memory_events, the following fields
   262→are irreversibly anonymised:
   263→
   264→  ----------------------------------------------------------------------------------------------
   265→  Field          Anonymisation Method                  Example
   266→  -------------- ------------------------------------- -----------------------------------------
   267→  GTID           Replaced with anonymous_entity_id—    SGTX-EG-TRD-002139-7F3A → anon_3847a92b
   268→                 deterministic hash using a rotating   
   269→                 pepper, changed every 90 days; old    
   270→                 mappings deleted after 30 days        
   271→
   272→  Exact amounts  Replaced with logarithmic bands       $45,000 → 'MEDIUM' ($10k-$100k)
   273→
   274→  Dates          Truncated to week (YYYY-WW) for most  2026-06-15 → '2026-W24'
   275→                 fields; delays stored as integer days 
   276→
   277→  Free‑text      Removed entirely; only categorised    "The shipment was delayed due to port
   278→  descriptions   fields remain                         strike"→ removed
   279→
   280→  Document       Never stored; only document type and  —
   281→  content        rejection reason                      
   282→
   283→  Email/phone    Never captured                        —
   284→  ----------------------------------------------------------------------------------------------
   285→
   286→Persistent Anonymous Entity ID Generation:
   287→
   288→rust
   289→
   290→use sha2::{Sha256, Digest};
   291→
   292→use chrono::Utc;
   293→
   294→fn generate_anonymous_id(gtid: &str, pepper: &str) -> String {
   295→
   296→let mut hasher = Sha256::new();
   297→
   298→hasher.update(gtid.as_bytes());
   299→
   300→hasher.update(pepper.as_bytes());
   301→
   302→let result = hasher.finalize();
   303→
   304→format!("anon_{:016x}",
   305→u64::from_be_bytes(result[0..8].try_into().unwrap()))
   306→
   307→}
   308→
   309→fn get_current_pepper() -> String {
   310→
   311→// Pepper changes every 90 days
   312→
   313→let days_since_epoch = Utc::now().num_days_from_ce() / 90;
   314→
   315→format!("pepper_{}", days_since_epoch)
   316→
   317→}

  1665→21.0 Purpose & Design Philosophy
  1666→
  1667→Every pallet, carton, or item that moves through a trade must leave an
  1668→unforgeable, instantly verifiable digital fingerprint. Barcodes are not
  1669→just stickers — they are the physical anchor of the platform's digital
  1670→twin. In v11.0, the barcode is intelligent, self‑sovereign, and
  1671→resilient. It carries exactly the data each party needs, can be verified
  1672→even without network access, and can be read by voice or camera when
  1673→physical labels fail. All generation, scanning, and verification runs on
  1674→open‑source libraries and zero‑cost infrastructure. The system supports
  1675→multiple symbologies (GS1‑128, Data Matrix, QR) and automatically
  1676→assigns globally unique SSCC18 codes to every logistic unit (pallet).
  1677→All scans trigger Governor‑gated milestone confirmations and are
  1678→immutably logged via Loom.
  1679→
  1680→The barcode system fully supports multi‑shipment contracts: each
  1681→shipment has its own set of pallets, each with a unique SSCC, and the
  1682→barcode includes the shipment USTN (or microUSTN for distressed splits).
  1683→The predictive scanning reliability agent (A2, XGBoost) proactively
  1684→warns warehouse managers if a batch of labels is likely to fail in the
  1685→intended environment. A detailed label print workflow ensures flawless
  1686→physical application from PDF to pallet, with a reprint policyenforced
  1687→by the Governor after pallets have been loaded. Blockchain
  1688→anchoring (Polygon) provides an immutable, publicly verifiable chain of
  1689→custody for high‑value cargo. Self‑sovereign pallet identity (W3C
  1690→Verifiable Credentials) allows offline verification using a pre‑cached
  1691→SGTX public key.
  1692→
  1693→Key principles (non‑marketplace, sovereign):
  1694→
  1695→-   Unforgeable identity — every barcode is cryptographically linked to
  1696→    its USTN and pallet record.
  1697→
  1698→-   Offline‑first — scanning, verification, and credential validation
  1699→    work without internet.
  1700→
  1701→-   Self‑sovereign — pallets carry their own verifiable credentials,
  1702→    signed by SGTX.
  1703→
  1704→-   Multi‑modal identification — barcode, visual recognition, and voice
  1705→    work interchangeably.
  1706→
  1707→-   Predictive reliability — AI predicts and prevents scan failures
  1708→    before they occur.
  1709→
  1710→-   Governor‑enforced reprint policy — prevents fraud after loading.
  1711→
  1712→-   Multi‑shipment aware — each shipment's pallets are independently
  1713→    tracked.

  1785→21.2 Barcode Generation & Dynamic Content (A1)
  1786→
  1787→21.2.1 SSCC18 Allocation
  1788→
  1789→During the packing plan lock (Phase 2, Part 3B.3.4),
  1790→the packing-containerisation-servicegenerates a globally unique Serial
  1791→Shipping Container Code (SSCC18) for every pallet. The SSCC conforms to
  1792→GS1 standard:
  1793→
  1794→Format: 1 (extension digit) + 0614141 (6‑digit company prefix reserved
  1795→for SGTX) + 123456789(9‑digit serial, unique per pallet) + 0 (check
  1796→digit)
  1797→
  1798→Example: 106141411234567890
  1799→
  1800→SSCC Generation Algorithm:
  1801→
  1802→rust
  1803→
  1804→fn generate_sscc(extension_digit: u8, company_prefix: &str, serial: u64)
  1805→-> String {
  1806→
  1807→let base = format!("{}{}{:09}", extension_digit, company_prefix,
  1808→serial);
  1809→
  1810→let check_digit = calculate_gs1_check_digit(&base);
  1811→
  1812→format!("{}{}", base, check_digit)
  1813→
  1814→}
  1815→
  1816→fn calculate_gs1_check_digit(base: &str) -> u8 {
  1817→
  1818→let mut sum = 0;
  1819→
  1820→for (i, c) in base.chars().enumerate() {
  1821→
  1822→let digit = c.to_digit(10).unwrap();
  1823→
  1824→if i % 2 == 0 {
  1825→
  1826→sum += digit * 3;
  1827→
  1828→} else {
  1829→
  1830→sum += digit * 1;
  1831→
  1832→}
  1833→
  1834→}
  1835→
  1836→let remainder = sum % 10;
  1837→
  1838→if remainder == 0 { 0 } else { 10 - remainder }
  1839→
  1840→}
  1841→
  1842→Multi‑shipment Support: For multi‑shipment contracts, the SSCC includes
  1843→an internal reference to the shipment number (encoded in the serial
  1844→range). Each shipment's pallets are assigned from a distinct serial
  1845→block.
  1846→
  1847→Distressed Micro‑contracts: When a distressed partial sale occurs (Part
  1848→3B.7), a new microUSTN is generated, and new SSCCs may be generated for
  1849→the split pallets (or existing ones retained with a flag). The mapping
  1850→is stored in pallet_details with micro_ustn reference.
