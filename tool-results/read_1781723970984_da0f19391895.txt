     1→PART 2 – IDENTITY, TENANTS & REGISTRATION
     2→2.0 Purpose & Design Philosophy
     3→The Identity & Tenants layer is the foundation of trust in SGTX. Every organisation that uses the platform – whether a trader, logistics provider, laboratory, QC inspector, customs broker, financier, or government agency – is assigned a cryptographically verifiable Global Trade Identity (GTID). The GTID is the permanent identifier for all actions, documents, and relationships.
     4→Key principles (nonmarketplace):
     5→• Selfsovereign – tenants control their own data; SGTX never shares GTID information without consent.
     6→• AIassisted onboarding – autocomplete, document extraction (HF Donut), and realtime validation against government registries reduce manual data entry. But AI never suggests “you might also want to trade with X”.
     7→• No unsolicited counterparty matching – the platform never recommends which tenants to connect with. All relationships are established outside SGTX and then explicitly added by users.
     8→• Flexible role hierarchy – supports dualmode for traders (Buyer/Seller toggle), business units, approval chains, and granular data scopes (e.g., hiding cost components from warehouse staff).
     9→All onboarding is zerocost, selfhosted, and uses free government registry APIs (scraped) for KYB/KYC verification.
    10→2.1 Global Trade Identity (GTID) – Format & Resolution
    11→Format: SGTX-{COUNTRY_CODE}-{ENTITY_TYPE}-{SEQUENCE}-{CHECKSUM}
    12→Example: SGTX-EG-TRD-002139-7F3A
    13→Components:
    14→• SGTX – fixed prefix.
    15→• COUNTRY_CODE – ISO 3166-1 alpha2 (e.g., EG, DE, VN).
    16→• ENTITY_TYPE – 3letter code (see table below).
    17→• SEQUENCE – zeropadded 6digit number, unique per (country, type).
    18→• CHECKSUM – 4hexadecimaldigit CRC32-ISO-HDLC of the concatenated fields.

   376→PART 2.8 – TRADE READINESS ASSESSMENT (FULLY EXPANDED, EXTENDED & DETAILED)
   377→Version 11.0 – Enhanced with AI Guidance, OneClick Remediation & Continuous Monitoring
   378→Purpose:

   539→2.8.3 Readiness Score Calculation
   540→Formula:
   541→text
   542→Readiness Score = (Completed Mandatory Items / Total Mandatory Items) × 100
   543→Note: Optional items do not count toward the mandatory completion percentage, but they are displayed in the UI as “Bonus” and may influence the tenant’s Trust Confidence Score (Part 10.12.1).
   544→Score Thresholds & Permissions:
   545→Score Range
   546→Status
   547→Can Create Trade?
   548→Restrictions
   549→100%
   550→Fully Ready
   551→✅ Yes
   552→None
   553→85–99%
   554→Mostly Ready
   555→✅ Yes (with warning)
   556→Warning only – user can proceed but advised to complete missing items
   557→70–84%
   558→Partially Ready
   559→⚠️ Limited
   560→Only preapproved corridors or lowvalue trades (<$10,000) allowed
   561→<70%
   562→Not Ready
   563→❌ No
   564→Trade creation blocked until score ≥70%

   590→2.8.5 OneClick Remediation Workflow
   591→For each missing item, the system provides a direct action link that:
   592→1. Opens a prefilled form (where possible).
   593→2. Guides the user through the required steps.
   594→3. Upon completion, automatically updates the checklist status and recalculates the readiness score.
   595→Example – Missing settlement account:
   596→• User clicks ConnectPSPConnectPSP.
   597→• Modal appears with a list of available PSPs (Fawry, PayMob, CBE IPN).
   598→• User selects a PSP and is redirected to the PSP’s OAuth flow.
   599→• After successful linking, SGTX receives a webhook and marks the item as completed.
   600→• The Readiness Card updates instantly (score increases).
   601→Example – Missing fee schedule acknowledgment:
   602→• User clicks Review & Sign.
   603→• Modal displays the current fee schedule (PDF + plainlanguage summary generated by Groq).
   604→• User clicks “I acknowledge and agree” (digital signature with passkey).
   605→• System records the signature in tenant_lifecycle_history and updates the checklist.
   606→ 
   607→2.8.6 AI Assistance (🧠 A1 – Groq)
   608→The AI generates plainlanguage, contextual recommendations for missing items. Recommendations are based only on the tenant’s own data and public defaults – never on “other tenants did this”.
   609→Examples:
   610→• “You haven’t added any shipping lines to your contacts. Adding at least one will help you get ocean freight quotes faster.”
   611→• “Your tax ID could not be verified automatically. Please check the number or upload a scanned certificate.”
   612→• “Your insurance certificate expires in 30 days. Renew it to maintain Full Ready status.”
   613→These recommendations appear below the checklist in the Readiness Card (collapsible).
   614→ 
   615→2.8.7 Continuous Monitoring & AutoRecalculation
   616→The readiness score is recalculated automatically whenever any of the underlying items change. Triggers include:
   617→• Periodic (daily) – Cron job reevaluates all tenants (e.g., tax ID expiry, certificate expiry).
   618→• Eventdriven – After a user completes an action via oneclick remediation.
   619→• External API webhook – e.g., PSP account linked, government registry update.
   620→If a previously completed item becomes invalid (e.g., passkey revoked, insurance expired), the score drops immediately and the user receives a Smart Inbox alert (priority 70) with a oneclick fix link.
   621→ 
   622→2.8.8 Integration with Governor (Trade Creation Block)
   623→When a user attempts to create a new trade (or financing request, or distressed declaration) and their current readiness score is <70%, the Governor returns a CONDITIONAL verdict with a Decision Panel (Part 12A.3) that:
   624→• Lists the missing items.
   625→• Provides direct action buttons for each missing item.
   626→• Includes an “Ignore and Proceed” button only if the score is between 70% and 84% (with a warning log).
   627→• For scores <70%, the “Proceed” button is disabled.

  1189→PART 2.10 – SGTX TRADE TRUST PASSPORT™
  1190→Version 11.0 – Fully Expanded, Extended & Detailed
  1191→Purpose:
  1192→Provide a portable, participantcontrolled institutional trust profile that aggregates a tenant’s reliability, compliance, financing performance, dispute resolution, and verified identifiers. The Trust Passport is a verifiable credential (W3C standard) signed by SGTX, enabling participants to share their trustworthiness with counterparties, financiers, logistics providers, and regulators without exposing raw trade data.
  1193→Key principles (nonmarketplace, sovereign):
  1194→• Participantcontrolled: No automatic sharing. Every share requires explicit consent.
  1195→• Privacypreserving: Passport contains aggregated scores and summaries, not transactionlevel details.
  1196→• Verifiable offline: Passport includes a cryptographic signature that can be verified using SGTX’s public key.
  1197→• Revocable: Sharing links can be revoked at any time; old links become invalid immediately.
  1198→• No ranking or discovery: The Passport never suggests “better” counterparties; it only reflects the tenant’s own verified history.

  1369→2.10.4 Sharing Workflow (OneClick)
  1370→Step 1 – Generate Passport
  1371→Tenant admin navigates to Company Admin → Trust Passport and clicks “Generate Passport” (one click).
  1372→• System creates a new verifiable credential.
  1373→• Passport is valid for 90 days (configurable per tenant).
  1374→• Admin sees a summary card with TRI, confidence, and expiration.
  1375→Step 2 – Share with Counterparty
  1376→Admin clicks “Share Passport” → selects the recipient’s GTID (from saved contacts) or chooses “Anyone with link” (anonymous token).
  1377→• If specific GTID, the system verifies that the recipient is an existing counterparty (already traded or added as contact).
  1378→• Admin selects which dimensions to share:
  1379→o ☑ Mandatory (TRI, confidence, status, verified identifiers, compliance summary) – always included.
  1380→o ☐ Optional dimensions (settlement_reliability, compliance_health, etc.) – consent per dimension.
  1381→o ☐ Financing summary – requires explicit consent.
  1382→o ☐ Dispute summary – requires explicit consent.
  1383→• Click “Generate Link” → system returns a onetime token URL (e.g., https://sgtx.io/trust/verify/vt-abc123).
  1384→• Admin copies link and sends to recipient (outside SGTX).
  1385→Step 3 – Recipient Verification
  1386→Recipient opens the link (no login required).
  1387→• Page displays the passport data (only the dimensions the sharer consented to).
  1388→• Recipient can download signed JSON or copy a verification code to check offline.
  1389→• The page shows a green checkmark if the signature is valid and the passport is not revoked or expired.
  1390→Step 4 – Revoke Access
  1391→At any time, admin clicks “Revoke” next to the shared token in the Trust Passport dashboard.
  1392→• Revocation is immediate.
  1393→• Any subsequent attempt to verify that token returns { "valid": false, "reason": "revoked" }.
  1394→Oneclick guarantee:
  1395→• Generate Passport (1)
  1396→• Share (1)
  1397→• Revoke (1)

  1515→2.10.10 Offline Verification & Public Key
  1516→Any party can verify a Trust Passport offline using the SGTX public key.
  1517→Steps (for recipient):
  1518→1. Download the signed passport JSON.
  1519→2. Use the opensource tool trust-verify (provided by SGTX) or run the following command:
  1520→bash
  1521→# Verify signature (requires sgtx-public-key.pem)
  1522→openssl dgst -sha256 -verify sgtx-public-key.pem -signature passport.sig passport.json
  1523→3. Check that the credential_hash matches the recomputed hash of the JSONLD (excluding the proof object).
  1524→4. Verify that expires_at is in the future.
  1525→Public keys are published at:
  1526→https://sgtx.io/.well-known/sgtx-keys (Ed25519 and optional Dilithium3 for archival).
